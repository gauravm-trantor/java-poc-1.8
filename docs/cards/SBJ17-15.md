# SBJ17-15 Move the workflow app's frameworks to versions that run on Java 17

Branch: `card/SBJ17-15-workflow-frameworks`. Part of SBJ17-1. SBJ17-20 (the Java 17 flip) waits on this card. Linked risk: end-of-life workflow frameworks may change how the approval process behaves.

## Assess, the card lead, 2026-11-28

### What the card changes

The workflow app (`workflow-app/`) runs a BPMN approval process on Activiti 5.22, behind a Spring MVC REST API served by an embedded Jetty. The person's decision of 2026-11-28 (in the card's description, and standing answer SA-5): Spring 4.3.30 to the latest 5.3.x, Activiti 5.22 kept, Jetty 9.4 to 12 in its EE8 (javax) mode, Jackson 2.9 to 2.18, H2 1.4 to 2.x. No jakarta.

### First step the person asked for: Activiti 5.22 on Java 17, unchanged

Logs and scripts in the programme folder, `.prime/tmp/SBJ17-15/` (`probe.sh`, `probe2.sh`, `repeat.sh`, `probe*.log`). Each run is `mvn -B -pl workflow-app -am test` in `maven:3.9.9-amazoncorretto-17` (Corretto 17.0.15), the code still compiled for Java 8.

1. main 067222d, nothing changed, JDK 17: 5 of 5 runs fail 22 of 30 workflow-app tests. Every one has the same cause, and it is Spring, not Activiti: Spring 4.3's CGLIB cannot call `ClassLoader.defineClass` on Java 17 (`InaccessibleObjectException: module java.base does not "opens java.lang"`), so the Spring context never starts. Activiti cannot be judged until Spring moves.
2. Only `spring.version` moved to 5.3.39 (Activiti 5.22, Jackson, Jetty, H2 and every test unchanged), on SBJ17-11's branch head 26984e3, which closes the timing race in the tests: 4 of 4 complete runs pass 47 of 47 workflow-app tests (30 existing and SBJ17-11's 17). One more run ended before its tests ran; the script did not keep why. So Activiti 5.22 runs on Java 17, and the person's condition for keeping it holds.
3. The same Spring-only change on main, without SBJ17-11: 3 of 3 runs fail 2 of 30, and which 2 changes from run to run (`approvedBatchIsPublished` and `sparkFailureFailsTheRunWithTheReason`, twice; `approvedBatchIsPublished` and `startReturnsBeforeTheBackgroundStepsFinish`, once; each "expected 1 but was 0", a step not yet finished). That is the timing race SBJ17-11 closes; on JDK 8 it failed 5 of 12 runs (SBJ17-11's card), on JDK 17 it shows in every run. With SBJ17-11 in, step 2 passed every complete run. So this card's Build should start from main after SBJ17-11 merges, or the pipeline will look red for a reason that is not this card's.

An earlier session also ran Spring 5.3.39, Jackson 2.18.2 and H2 2.2.224 together (Jetty and Activiti unchanged): JDK 8, 30 of 30 workflow-app tests pass (`e2-jdk8.log`); JDK 17, 28 of 30, the 2 failures being the timing race (`e2-jdk17.log`).

### Is it one slice

No, as written. Jetty 12 is built for Java 17 and needs it to compile and run, but the pipeline stays on JDK 8 until SBJ17-20 flips it, and SBJ17-20 waits on this card. So Jetty 12 cannot land on main before the flip. Spring 5.3, Jackson 2.18 and H2 2.x run on Java 8 and Java 17 alike, so they can land now and the flip finds them ready. Spring must move before the flip in any case (step 1 above).

Second, Jetty 12 renames the servlet package, and `LocalDebugServer.java` (in the test tree, a launcher run by hand, with no tests in it) imports the old names. The programme keeps existing tests unchanged (standing answer SA-2); whether this file counts is the person's call.

Proposed slices (asked of the person, one question):
- This card: Spring 5.3.x, Jackson 2.18, H2 2.x, Activiti 5.22 kept, Jetty left at 9.4.44, all on Java 8, proven on Java 17 locally.
- A new card after SBJ17-20: Jetty 9.4 to 12 in EE8 mode on Java 17, with the import-only change to `LocalDebugServer.java`.

### Known gap (from the card, not solved here)

Spring 5.3 no longer gets free security fixes and Activiti 5.22 gets none, so the security scan may still flag them.

### Decisions I took (standing answer SA-3)

- The probes ran in Corretto containers, as EMR 7.14.0 uses Corretto 17.
- The baseline is the pipeline run on main, not a local run, because the local runs carry the timing race.
