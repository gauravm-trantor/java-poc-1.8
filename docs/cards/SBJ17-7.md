### Change map

- The order dependency lives in `workflow-app/src/test/java/com/example/salesbatch/workflow/`: every Spring test class shares one cached context (`AppConfig`, `TestInfraConfig`). `PublishDelegate` reads `report.dir` once, when that context is built (`@Value("${report.dir:/tmp/sales-batch-reports}")`, and `application.properties` has `report.dir=/tmp/sales-batch-reports`).
- `BatchControllerTest`, `BatchControllerUploadTest`, `SalesBatchProcessTest` and `WorkflowServerTest` set `report.dir` to `<java.io.tmpdir>/sales-batch-test-reports` before the context is built. `WebConfigTest` and `DataControllerTest` do not. When either runs first, the context points at `/tmp/sales-batch-reports` and `SalesBatchProcessTest.approvedBatchIsPublished` reads its report from the other folder.
- Places the fix may land without changing a test: `workflow-app/pom.xml` (Surefire system properties: `report.dir`, and a `java.io.tmpdir` under `target/`), and `.github/workflows/ci.yml` (drop the forced order) once SBJ17-2 is merged. `TestInfraConfig.java` is a test support class, not a test, but it sits beside the tests; see the decisions below.
- No production code needs to change for the order dependency.

### What the change would really do: the order sweep

This card changes no production code, so a side-by-side run of the report on sample-data has nothing to compare (the Java 8 build is the same before and after). The question Assess must answer is which orders fail and why. Sweep scripts: `sweep.sh` and `webfirst.sh`, output in `sweep/`, all in `<programme>/.prime/tmp/SBJ17-7/`.

12 runs of the 30 `workflow-app` tests: alphabetical 3, reverse alphabetical 2, random 6, plus the default run. 5 of the 12 had a failure. Three groups:

1. **Report folder fixed by whichever test class runs first (the card's subject).** Proven on an empty temp folder (`webfirst.sh`): `WebConfigTest` then `SalesBatchProcessTest` fails `approvedBatchIsPublished` with `NoSuchFileException ...\sales-batch-test-reports\report-20261113.csv`; the report went to `C:\tmp\sales-batch-reports`. The other order passes. Reverse alphabetical hides it, because `WorkflowServerTest` sets the property before `WebConfigTest` builds the context.
2. **Leftover reports from earlier runs hide group 1.** The tests never clear `<temp>/sales-batch-test-reports`, and this laptop holds `report-20261113.csv` there from earlier runs. So the random runs with `WebConfigTest` first passed locally, reading a stale report. A fresh runner has no leftover and fails. Same cause family as group 1; a test temp folder under `target/` (wiped by `mvn clean`) removes it.
3. **A timing race, in every order (outside "any order").** `SparkJobDelegate` writes the status `WAITING_APPROVAL` to the audit store before Activiti commits the approval task. `Await.status` returns as soon as it sees the status, and the test then finds no task. Seen 5 times in 12 runs across alphabetical, reverse and random orders. Examples: `approvedBatchIsPublished:73 expected:<1> but was:<0>` (task count), `rejectedBatchIsNotPublished: IllegalStateException: No pending approval for process instance 49`, `sparkFailureFailsTheRunWithTheReason:107 expected null, but was:<ProcessInstance[108]>`. Not order-related; the same gap exists for a real client that polls the status and then approves at once.

### Is it one slice

Groups 1 and 2 are one slice a person can try: run the tests in any order on an empty temp folder and they pass. Group 3 is a separate problem with a different fix (the test helper or the order of the status write in production code) and a different proof (repeated runs). Proposed split: this card covers groups 1 and 2; a new card covers group 3, after this one.
