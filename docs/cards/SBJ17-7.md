### Design

**The cause, in one line.** All Spring test classes share one cached context. `PublishDelegate` reads `report.dir` once, when that context is built. Four test classes set `report.dir` before that; `WebConfigTest` and `DataControllerTest` do not. Whichever class runs first decides the folder for the whole run.

**The fix.** Give the forked test JVM the values before any test class loads, in `workflow-app/pom.xml`, Surefire `configuration`:

```xml
<argLine>-Djava.io.tmpdir=${project.build.directory}</argLine>
<systemPropertyVariables>
  <report.dir>${project.build.directory}${file.separator}sales-batch-test-reports</report.dir>
</systemPropertyVariables>
```

Why each part:

- `report.dir` is set before the first context is built, so the order no longer matters. It is the same path the four test classes compute (`<java.io.tmpdir>/sales-batch-test-reports`), so when they set it again they set the same value, and `SalesBatchProcessTest` reads the report where `PublishDelegate` wrote it. That covers AC1 and AC2.
- `java.io.tmpdir` points at `workflow-app/target`, which always exists when tests run (it holds `test-classes`) and which `mvn clean` wipes. So leftover reports from earlier runs (Assess, group 2) cannot hide a failure, and the reports, uploads (`sales-batch-uploads`) and multipart files stay inside `target/`. That covers AC3. It is set on the command line (`argLine`), not as a system property variable, because the JDK caches the temp folder the first time it is used, which can be before Surefire sets its variables.
- No production file, test or test support class changes (answer item 2, SA-2). `application.properties` keeps `report.dir=/tmp/sales-batch-reports` for the running app.
- The local checkout path has spaces (`Genpact RiskCanvas`), and Surefire splits `argLine` on spaces. Build checks this first on the laptop. If the unquoted form breaks, the fallback order is: quote the value inside `argLine`; else set `java.io.tmpdir` in `systemPropertyVariables` too and confirm every temp use in the module reads `System.getProperty` (the three in Assess's change map do). Build records which form it used and why.
- `argLine` is not set anywhere else in the build (checked: no other pom names it), so nothing is overwritten.

**The pipeline (AC4).** SBJ17-2's `ci.yml` runs `mvn -B clean test -Dsurefire.runOrder=alphabetical` with a comment that names this problem. SBJ17-2 is in Offered, not yet merged. If it is merged before Build, Build rebases this branch on `main` and removes the `-Dsurefire.runOrder=alphabetical` flag and its comment. If it is not merged when Build ends, the change to `ci.yml` cannot be made on this branch without copying SBJ17-2's file; Build records the gap and AC4's pipeline half is checked by its script against whatever `ci.yml` is on the branch.

**The acceptance tests.** These criteria are about how the test suite runs, so the acceptance tests are pipeline checks, not JUnit classes: a JUnit class cannot choose the order of other classes, and inside the same JVM it would reuse the cached context. They follow SBJ17-2's pattern (named steps that start with the criterion number, scripts in `scripts/ci/`):

- New workflow `.github/workflows/test-order.yml`, on pull requests to `main` and pushes to `main`, JDK 8 Temurin, `ubuntu-24.04`. A fresh runner has an empty temp folder, so no leftover report helps.
- Scripts in `scripts/ci/test-order/`, one per criterion, plain `sh`, also runnable on a laptop:
  - `AC1-any-order.sh <order>`: runs the `workflow-app` tests (`-pl workflow-app -am`, `-Dtest=com/example/salesbatch/workflow/**/*Test -DfailIfNoTests=false`) with `-Dsurefire.runOrder=<order>`, `TMPDIR`/`TMP`/`TEMP` pointed at a new empty folder. The workflow runs it as a matrix: `alphabetical`, `reversealphabetical`, `random`. Job names "AC1 tests pass in <order> order".
  - `AC2-webconfig-first.sh`: `-Dtest=WebConfigTest,SalesBatchProcessTest -Dsurefire.runOrder=reversealphabetical` (W before S), empty temp folder. Assess showed this fails today on an empty temp folder.
  - `AC3-reports-inside-target.sh`: clears `/tmp/sales-batch-reports`, runs the `workflow-app` tests with an empty temp folder, then fails if any `report-*.csv` exists outside `workflow-app/target/` (it looks in the temp folder, `/tmp/sales-batch-test-reports`, `/tmp/sales-batch-reports`, and the repository outside `target/`). Today it fails: the report goes to `<temp>/sales-batch-test-reports`.
  - `AC4-tests-unchanged-no-forced-order.sh <base>`: fails if any file under `*/src/test/` that exists on `<base>` is changed or deleted on this branch, and fails if any file in `.github/workflows/` passes `surefire.runOrder` to the main Maven test step (`test-order.yml` itself is excluded, because AC1 uses the flag on purpose). "All existing tests pass" is the AC1 runs (all 30 `workflow-app` tests) plus SBJ17-2's `CI / maven` job (67 tests) once it is on the branch.
- "Empty temp folder" on each system: Java on Windows takes its temp folder from `TMP`/`TEMP`, so the scripts point those at a new empty folder. Java on Linux ignores `TMPDIR` and always uses `/tmp`, so on Linux the scripts delete `/tmp/sales-batch-test-reports` and `/tmp/sales-batch-reports` before the run. The scripts never pass `argLine` or `report.dir` themselves, because that would override the fix under test.
- Each step runs `if: always()` so one red criterion does not hide the others.

**What the red run before Build should show.** AC2 red, AC3 red. AC1 alphabetical and reverse may pass (reverse hides the problem; see Assess group 1); AC1 random fails only when `WebConfigTest` or `DataControllerTest` comes first. AC4 red only if `ci.yml` with the forced order is on the branch. AC2 and AC3 red is enough to show the tests see the problem.

**The timing race and AC1.** SBJ17-11's race fails about 5 runs in 12, in any order (Assess group 3). Until SBJ17-11 is built, an AC1 job can fail for that reason alone. Rules for this card, so a race failure is neither hidden nor counted as this card's:
- The scripts never retry and never filter. A red job stays red on record.
- Build judges a red AC1 job by its failure: the race signatures recorded in Assess (`approvedBatchIsPublished ... expected:<1> but was:<0>`, `No pending approval for process instance`, `sparkFailureFailsTheRunWithTheReason ... expected null`) count against SBJ17-11; a `NoSuchFileException` on the report, or any other failure, counts against this card. Build reruns the whole workflow and records every run in the card file. AC1 holds when each order has a run with all 30 tests passing, and no run shows an order failure.
- If SBJ17-11 is built first, this rule falls away.

**Sensitivity check (prime:evidence).** After Build, remove the two pom lines in a scratch copy and run AC2 and AC3: both must turn red. That shows the checks notice the problem coming back.
