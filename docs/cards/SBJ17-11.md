### What the change really does

The cause. Ingest and Spark run in the Activiti job executor, inside a database transaction. The audit store (HBase, or the in-memory store in tests) is not part of that transaction. `SparkJobDelegate` writes `WAITING_APPROVAL`, and `RunFailure.mark` writes `FAILED`, while the transaction is still open. The approval task is created, or the run is ended, only when it commits. A client polling `status` can see the new status first and act too early.

The fix this card needs: the two statuses are written only after the transaction commits (for example with an Activiti transaction listener on `COMMITTED`), so a status a client sees is always true in the engine. What it keeps: the statuses, their order, the error text, the BPMN file, the HBase table layout and every existing test. A real client gains: approve at once after `WAITING_APPROVAL` no longer gets "No pending approval".

### Design

The two statuses a client acts on, `WAITING_APPROVAL` and `FAILED`, are written to the audit store only once the engine's transaction has committed. Then the approval task exists, or the run has ended, before any client can see the status.

How. Activiti 5.22 lets a step add a listener to the running command's transaction: `Context.getCommandContext().getTransactionContext().addTransactionListener(TransactionState.COMMITTED, ...)`. With `SpringProcessEngineConfiguration` this becomes a Spring `afterCommit` callback on the job's transaction (the job executor runs each job through the Spring transaction interceptor).

- New package-private helper `AfterCommit` in `.../workflow/delegate/`: `AfterCommit.run(Runnable)` adds the listener. Outside a command (no command context) it runs the write at once, so the code is still usable from a plain unit test.
- `SparkJobDelegate`: `repository.updateAudit(pid, "WAITING_APPROVAL", null)` goes through `AfterCommit.run`.
- `RunFailure.mark`: `recordError` then `updateAudit(pid, "FAILED", null)` go through one `AfterCommit.run`, in that order, so the reason is there before the status. `execution.setVariable("failed", true)` stays in the transaction: the gateway reads it.
- A write that throws after the commit is caught and logged with the run id; the job has already committed, so throwing would only reach the job executor's failed-job handling for a job that no longer exists.
- Unchanged: `IngestDelegate` (`RUNNING`), `AuditStartListener` (`QUEUED`), `PublishDelegate`/`RejectDelegate` (written inside the caller's own `approve` request, which returns after the commit), the BPMN file, `EngineConfig`, the HBase table layout, the statuses and their order, the error text.

### How each criterion is proved (for Test design)

The race is hard to hit on purpose, so the new tests widen it. The new test class uses the same Spring context as `SalesBatchProcessTest` (`AppConfig` + `TestInfraConfig`, so no second engine) and, for its own run id only, adds an Activiti event listener at runtime (`runtimeService.addEventListener`, removed in `@After`) that holds the job thread for about one second on `TASK_CREATED` (AC1) or `PROCESS_COMPLETED` (AC2). Both events fire inside the job's transaction, after today's status write and before the commit, so today the gap becomes a second wide and the test fails every time; after the fix the status is written only after the commit, so the hold changes nothing a client sees.

### Decisions I took (SA-3)

- Transaction listener over the alternatives: making `BatchService.status` check the engine (changes what `status` reads, and the HBase audit is what other readers see), or a BPMN change (the process file must not change).
- Only the two statuses a client acts on move. `COMPLETED` and `REJECTED` are written inside the `approve` request, which returns after its commit, so a caller of `approve` never sees them early; not in the criteria, left alone.
- Test method names `AC1_...`, `AC2_...` (a Java name cannot start with a digit); scripts `ACn-*.sh` as card SBJ17-7 did.

### Review of the design

A helper with fresh context could not be started: this run has no subagent tool, and starting `claude -p` from the shell needs a permission this non-interactive run does not have. **Gap**: the fresh-context read is still owed; the blind review after Build reads the code with fresh context, and the next card lead may run the helper if it can. I read the design against the code myself, adversarially; findings and how each is settled:

1. A widening test with its own Spring config would start a second engine on the same in-memory database (`jdbc:h2:mem:activiti`), and the cached context's job executor could take the new test's jobs and write to the other repository. Resolved: the new test shares the existing context and widens the gap with a runtime event listener instead (design above).
2. Does `COMMITTED` fire after the job's commit? Yes: `SpringProcessEngineConfiguration` uses `SpringTransactionContext`, whose `COMMITTED` listener is a Spring `afterCommit` callback, and the job executor runs each job through the Spring transaction interceptor. Build checks it with the AC1 and AC2 tests.
3. Would the old code fail, not block? H2 1.4.197 uses MVStore with multi-version reads by default, so a reader sees the committed state at once; the baseline's failures (`expected:<1> but was:<0>`, not a lock timeout) show it. Answered.
4. A failure path changes: today an audit store that throws on `WAITING_APPROVAL` rolls the job back and the job executor retries the step (Spark runs again). After the fix the job has committed, so the write is logged with the run id and the status stays `RUNNING`. Answered: HBase down is outside the agreed inputs, and rerunning Spark to retry an audit write was not a designed behaviour; recorded here for Verify. On a rolled-back job the new code writes nothing, where today it can leave a status that never happened, which is the gap itself.
5. `Context.getCommandContext()` outside a command returns null in Activiti 5.22, so `AfterCommit.run` writes at once there. Build adds a small unit test for it.

### Review of the code, and a residual for the reviewer

No subagent tool in this run, so no helper with fresh context read the build; the blind review is the fresh read. My own adversarial read:

1. Ingest failures also go through `RunFailure.mark`, so their `FAILED` also moves after the commit; `RUNNING` is still written first. Order kept.
2. A rolled-back job writes nothing now; the retry writes the status once it commits.
3. Residual, new but narrow: `approve` looks for the approval task, not the status. A caller who approves on the task alone (not by polling the status) in the moment between the Spark job's commit and its after-commit write could have `COMPLETED` written before the late `WAITING_APPROVAL`, leaving the status stuck at `WAITING_APPROVAL`. The window is the time between Spring's commit and the next line on the same thread; every client in this repository waits for `WAITING_APPROVAL` first. Left as is and named here for review; a guard would add a read before the write.
4. A failure of the audit write after commit is logged with the run id and not retried (Plan, finding 4).
