### Design

The data stack moves in the build files and two Docker images. The Java and Scala code needs nothing for the move itself; two deprecated HBase calls are swapped in a separate, last step.

**Build (poms).** Root `pom.xml`: `scala.version` 2.12.18, `scala.binary.version` 2.12, `spark.version` 3.5.8, `hadoop.version` 3.4.2, `hbase.version` 2.6.4, a new `zookeeper.version` 3.9.3 managed in `dependencyManagement` (HBase 2.6.4 and Hadoop 3.4.2 both bring 3.8.x), shade plugin 3.2.4 to 3.6.0. `java.version` stays 1.8. `spark-job/pom.xml`: `hbase-server` is replaced by `hbase-mapreduce` (HBase 2 moved `TableInputFormat` there; it still brings `hbase-server`), keeping the same exclusions; Scala's `-target:jvm-1.8` stays. No `--add-opens` (that is slice 2). This is the Assess probe's pom change minus the Java 17 parts (`docs/cards/SBJ17-14/probe-poms.diff`).

**HBase 2.6.4 container.** `harisekhon/hbase` has no 2.6 image, so the repository gets its own: `docker/hbase/Dockerfile`, from `amazoncorretto:8` named by its digest (as SBJ17-9 did for the old image), with Apache's `hbase-2.6.4-hadoop3-bin.tar.gz` checked against Apache's published SHA-512 in the Dockerfile. HBase unpacks to `/hbase` with `/hbase/bin` on `PATH`, so `start-hbase.sh` (copies to `/hbase/conf`) and the pipeline's wait loop (`docker exec sales-hbase hbase shell`) work unchanged. If Apache publishes no `-hadoop3` binary for 2.6.4, the default binary is used and the card file says so. It runs HBase in one container (`hbase.cluster.distributed=true`, `HBASE_MANAGES_ZK=true`: ZooKeeper and the master started as daemons, the region server in the foreground) with HBase's own ZooKeeper on 2181, master 16000, region server 16020, web UI 16010, as the old image did. The `hbase` service in `docker/local/docker-compose.yml` builds it (`build: ../hbase`, `image: salesbatch-hbase:2.6.4`), keeps the container name `sales-hbase`, the ports and the `host.docker.internal` trick of `start-hbase.sh` (its last line changes from the old image's `/entrypoint.sh` to starting HBase in the foreground). `hbase-server-site.xml` is checked against 2.6 and changed only where 2.6 needs it (for example `hbase.unsafe.stream.capability.enforce=false` on a local file system). Java 8 inside, so the whole AC4 run is Java 8; slice 2 moves it to 17.

**Spark runtime image.** `docker/Dockerfile`: Spark 3.5.8 (`spark-3.5.8-bin-hadoop3.tgz`, SHA-512 checked) instead of 2.4.8, base image unchanged (`eclipse-temurin:8-jre-jammy`, Java 8). Note: Spark's own binary bundles Hadoop 3.3.x client jars, not 3.4.2; that is the local stand-in for EMR's cluster, where the job's provided Spark and Hadoop come from EMR. SBJ17-17 pins the same `FROM` line by digest; whichever merges second takes the other's line.

**Pipeline.** `.github/workflows/ci.yml`, `maven` job: `docker compose ... up -d --build hbase` (builds the new image), the wait loop and `scripts/ci/AC4-hbase-tests-ran.py` unchanged, JDK 8 unchanged. The card's acceptance checks run in a job `acceptance-sbj17-14`, only on this card's pull request (`if: github.head_ref == 'card/SBJ17-14-data-stack-emr7'`), as SBJ17-2 and SBJ17-9 did, using only the steps already pinned in `ci.yml`.

**Deprecated HBase calls (last step, no behaviour change).** `RowFilter(CompareFilter.CompareOp.EQUAL, ...)` becomes `RowFilter(CompareOperator.EQUAL, ...)` in `SalesAggregator.scala` and `HBaseSalesRepository.java`; `new Scan(start, stop)` becomes `new Scan().withStartRow(start).withStopRow(stop)` (start inclusive, stop exclusive, as before). `HBaseTables` keeps `HTableDescriptor`/`HColumnDescriptor`, because the existing tests verify `createTable(any(HTableDescriptor.class))` (SA-2; risk SBJ17-18). If any existing test notices this step, the step is dropped: it is not needed for any criterion.
