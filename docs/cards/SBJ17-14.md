### Change map

- `pom.xml` (root): version properties (`scala.version`, `scala.binary.version`, `spark.version`, `hbase.version`, `hadoop.version`, `java.version`), a ZooKeeper 3.9.3 pin in `dependencyManagement` (HBase 2.6.4 brings an older one), shade plugin 3.2.4 to 3.6.0 (see below).
- `spark-job/pom.xml`: `hbase-mapreduce` (HBase 2 moved `TableInputFormat` and `TableMapReduceUtil` out of `hbase-server`); the Scala `-target:jvm-1.8` argument; Surefire `--add-opens` for Spark on Java 17 (late-bound `@{argLine}`, keeps JaCoCo).
- `common/pom.xml`: nothing beyond the version property, from the probe.
- `spark-job/src/main/scala/.../SalesAggregator.scala`: `RowFilter(CompareFilter.CompareOp.EQUAL, ...)` is deprecated in HBase 2 (it still compiles). `common/.../HBaseSalesRepository.java` has the same filter and `new Scan(start, stop)`; `common/.../HBaseTables.java` uses `HTableDescriptor`/`HColumnDescriptor`. All deprecated, all still in 2.6.4.
- The existing tests pin two of these: `HBaseTablesTest` and `HBaseSalesRepositoryTest` verify `createTable(any(HTableDescriptor.class))`, and `HBaseSalesRepositoryTest:138` checks the filter is a `RowFilter`. Since the tests stay unchanged (SA-2), `HBaseTables` must keep passing an `HTableDescriptor`; the filter may move to `CompareOperator` (still a `RowFilter`).
- `docker/Dockerfile`: Spark 2.4.8 on `eclipse-temurin:8-jre` becomes Spark 3.5.8 (Hadoop 3 build) on Corretto 17. `docker/local/docker-compose.yml`: `harisekhon/hbase:1.4` has no 2.6 tag, so the HBase 2.6.4 container needs an image of our own (from the Apache binary), with `start-hbase.sh` and `hbase-server-site.xml` checked against 2.6.
- `.github/workflows/ci.yml`: JDK, and the HBase container the `maven` job starts.
- Entry points: `SalesAggregator.main` (spark-submit), `workflow-app`'s `PublishDelegate` writes `report-<date>.csv` from `sales_agg`.

Differences found, by group:

1. **Line ends follow the operating system, not the Java version.** My first run put the old side on Windows and the new on Linux: every line differed by CR. `PublishDelegate` uses `Files.write`, which writes the platform's line separator. Not a version difference; the side-by-side must run both sides on the same OS (Build: both in Linux containers, as EMR is).
2. **Shade 3.2.4 cannot build the fat jar.** `Unsupported class file major version 65` on `hbase-shaded-jersey-4.1.12.jar` (Java 21 classes in a multi-release jar, pulled in by `hbase-server` 2.6.4). Shade 3.6.0 builds it. The fat jar grows to 58.7 MB; depending on `hbase-mapreduce` and `hbase-client` instead of `hbase-server` may shrink it (Plan decides, it is machinery).
3. **workflow-app does not start on Java 17 with Spring 4.3.** `InaccessibleObjectException: module java.base does not "opens java.lang"` from Spring's CGLIB, in `BatchControllerTest`, `BatchControllerUploadTest`, `DataControllerTest` (10 tests). That is SBJ17-15's work (Spring 5.3). So "every module builds on JDK 17" cannot hold until SBJ17-15 is done.
4. **The one workflow-app failure on Java 8 is the known race.** `SalesBatchProcessTest.approvedBatchIsPublished:73 expected:<1> but was:<0>`, the SBJ17-11 signature, not this change.

No difference in the aggregated figures, their order or their formatting.

Not yet measured (Build): the 2 HBase tests against a real HBase 2.6.4; the job reading and writing HBase through `TableInputFormat` on Spark 3.5; the end-to-end report.

### Is it one slice (INVEST)

- Independent: no. The Java 17 part needs SBJ17-15 first (group 3). The data stack part does not: on Java 8 it builds and passes.
- Negotiable: yes; the card names versions, not a design.
- Valuable: yes, both parts (supported data stack; supported runtime).
- Estimable: the data stack on Java 8 yes; the Java 17 flip only once SBJ17-15's shape is known.
- Small: together about one day and well under 400 lines, but two concerns with different proofs and a dependency between them.
- Testable: each part has its own proof: the pipeline plus a side-by-side of main against the new stack, both on Java 8; then Java 8 build against Java 17 build.

The first part that could merge by itself: the data stack on Java 8. So the card is two slices (pattern "prepare on the old runtime, then flip").

Why not split the data stack further: Spark 3.5 needs Hadoop 3 client libraries, and HBase 1.4's `TableInputFormat` is built for Hadoop 2. Spark, Hadoop and HBase move together, as the card says.
