What follows from the logs:

1. **Every refusal came on a cache miss.** With a hit (run 46022251225) Maven downloads nothing and cannot be refused.
2. **`setup-java`'s cache misses whenever any `pom.xml` changes**: its key is a hash of the poms and it has no fallback key, so it starts from an empty repository and downloads everything (about 68 MB). It also saves only after a green job, so a red run on a new key leaves the next run cold too. The Java 17 cards (SBJ17-14, SBJ17-15) change every pom, so they would hit this on every first run.
3. **Maven already retries**: 3 retries at 5, 10 and 15 seconds (Maven 3.9's default). That 30 seconds is too short for Maven Central's rate limit to lift. Longer and more retries would help; a retry alone would not fix a cold cache.
4. Up to five Maven jobs per pull request start at once (`CI / maven`, three `any-order`, `reports`), each downloading on a miss, which adds to the load on Maven Central from one runner pool.

### Design

**The Maven jobs.** A Maven job is any job with an `actions/setup-java` step. Today: `CI / maven`,
`Test order / any-order` (three in a matrix), `Test order / reports`; after SBJ17-11, `Repeat tests / twenty-runs`.

**1. Restore with a fallback (AC1).** In each Maven job, `setup-java` loses `cache: maven` (it keys on the
pom hash with no fallback and saves only on success). In its place, right after `setup-java`:

```yaml
- name: Restore the Maven repository
  id: maven-cache
  uses: actions/cache/restore@<commit> # <release>
  with:
    path: ~/.m2/repository
    key: maven-${{ runner.os }}-${{ github.job }}-${{ hashFiles('**/pom.xml') }}
    restore-keys: |
      maven-${{ runner.os }}-${{ github.job }}-${{ hashFiles('**/pom.xml') }}-partial-
      maven-${{ runner.os }}-${{ github.job }}-
      maven-${{ runner.os }}-
      setup-java-${{ runner.os }}-x64-maven-
```

- An exact key restores as today. With changed poms there is no exact key, and GitHub restores the newest
  cache whose key starts with a restore key, tried in order: first a partial cache of these same poms, then
  this job's newest cache, then any job's, then the caches `setup-java` saved before this change (key seen in
  run 46022251225: `setup-java-Linux-x64-maven-<hash>`), so the first run after the change is warm too.
- One key per job (`github.job`): the Test order jobs build only `workflow-app`, so their repository is smaller
  than `CI / maven`'s. Sharing one key would let the smaller one win the save and leave `CI / maven` downloading.
  The three matrix jobs share a key; they need the same files. About 68 MB per job, four keys per pom hash: far
  under the repository's 10 GB cache limit.

**2. Save even when tests fail (AC2).** Two steps at the end of each Maven job, after every other step:

```yaml
- name: Save the Maven repository
  if: success() && steps.maven-cache.outputs.cache-hit != 'true'
  uses: actions/cache/save@<commit> # <release>
  with:
    path: ~/.m2/repository
    key: ${{ steps.maven-cache.outputs.cache-primary-key }}
- name: Save the Maven repository, run failed
  if: failure() && steps.maven-cache.outputs.cache-hit != 'true'
  uses: actions/cache/save@<commit> # <release>
  with:
    path: ~/.m2/repository
    key: ${{ steps.maven-cache.outputs.cache-primary-key }}-partial-${{ github.run_id }}-${{ github.run_attempt }}
```

- A cache key can be saved only once. A red run saves under a `-partial-` key, so it never takes the full key:
  the next run of the same poms restores the partial cache (first restore key), downloads only what is missing,
  and on green saves the full key. A partial cache never becomes the exact hit that stops the full one being saved.
- When three matrix jobs save the same key at once, one saves and the others log "Unable to reserve cache" as a
  warning; the job stays green. That is `actions/cache/save`'s own behaviour.
- A cancelled run (a newer push) saves nothing; the newer run carries on.

**3. Longer retries (AC3).** A workflow-level `env` in each workflow that has a Maven job:

```yaml
env:
  MAVEN_ARGS: -Daether.connector.http.retryHandler.count=6 -Daether.connector.http.retryHandler.interval=10000
```

- Maven 3.9 reads `MAVEN_ARGS` on every `mvn` call, including those inside `scripts/ci/test-order/common.sh`
  and SBJ17-11's script, so no script changes.
- Maven Resolver 1.9 waits `interval x attempt` between tries (the logs show 5, 10, 15 s with the defaults 3 and
  5000 ms) and treats 429 and 503 as "retry". With 6 and 10000 ms it tries 7 times over 10+20+30+40+50+60 = 210 s
  (3.5 minutes) before giving up, and honours a `Retry-After` header. AC3 needs at least 5 retries over a minute.
- Not `.mvn/maven.config`: that would change every local build, and `.mvn/` is not on the programme's "may change"
  list. `MAVEN_ARGS` keeps the change inside the pipeline files.
- Maven older than 3.9 ignores `MAVEN_ARGS`. The test for AC3 runs the runner's own `mvn`, so it fails if the
  runner's Maven does not honour it (the runner's version goes in the card file at Test design).

**4. Pins.** The new `actions/cache/restore` and `actions/cache/save` are pinned by full commit with the release
in a comment, as SBJ17-9 does for every `uses:`. The commit is taken from the action's newest release at Build.

**What does not change (AC4).** No pom, Java or Scala source, existing test, script under `scripts/ci/test-order/`
or `.mvn/`. The `ui` job keeps `setup-node`'s npm cache (npm was not refused). The HBase image and every other step stay.

### Design review

**Gap: no helper with fresh context could be started.** This session has no tool to start a subagent, and
running the `claude` command line from the shell needs a person's approval. So the exit criterion "a helper with
fresh context read the design" is not met. I read the design back against the workflow files and the
`actions/cache` documentation myself; the findings and what I changed:

| # | Finding | Resolved |
|---|---|---|
| 1 | If a job fails before the restore step (checkout or `setup-java`), the restore step has no outputs, so the save steps would run with an empty key and fail with a key error | Both save conditions also need `steps.maven-cache.outcome == 'success'` (below) |
| 2 | `cache-hit` is `'true'` only on an exact key match, not on a restore-key match | Holds as designed: a run restored from an older key saves its own key |
| 3 | AC3's test needs Maven to download something. `mvn validate` on the project may download nothing | The test runs an explicit plugin goal (`maven-help-plugin`) with an empty local repository, so the first request is always a download |
| 4 | 7 tries over 3.5 minutes per refused file: a fully refused cold run now takes longer to fail | Accepted: it fails either way, and `twenty-runs` has a 60-minute limit, far above it |
| 5 | Red runs on pull requests add one `-partial-` cache each | Accepted: GitHub drops caches unused for 7 days and the oldest past 10 GB |
| 6 | SBJ17-11's `repeat-tests.yml` names `actions/checkout@v7` and `actions/setup-java@v6` by label, not commit, undoing SBJ17-9's pinning | Outside this card: raised as a risk note on SBJ17-11. This card pins only the two cache actions it adds |

A Build-time reviewer (the blind reviewer) reads the change with fresh context in Review.

The save conditions, as revised:

```yaml
if: success() && steps.maven-cache.outcome == 'success' && steps.maven-cache.outputs.cache-hit != 'true'
if: failure() && steps.maven-cache.outcome == 'success' && steps.maven-cache.outputs.cache-hit != 'true'
```
