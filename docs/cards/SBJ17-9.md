# SBJ17-9 Pin the pipeline's building blocks to exact versions

Branch: `card/SBJ17-9-pin-pipeline`. Comes from risk SBJ17-8 (decided: mitigate) and risk SBJ17-3 (decided: mitigate, pin by digest and keep a copy).

## Assess, the card lead, 2026-11-27

### What the card changes

The pipeline names its ready-made steps by a moving label (`actions/checkout@v7`) and pulls the HBase image by a moving tag (`harisekhon/hbase:1.4`). A publisher can move a label, so the pipeline could change without a commit of ours. The card replaces each label with the exact commit it points to today, and the image tag with its digest. Nothing the tests do changes.

### Change map

| What | Where |

| Entry points | The pipeline runs on each pull request to main and each push to main. Checks required on main: `maven`, `ui` |

Out of scope, and why (my decision, standing answer SA-3):
- `docker/Dockerfile` (`eclipse-temurin:8-jre-jammy`): the pipeline does not build or use it, and the Java 17 work will replace that base image anyway.
- `runs-on: ubuntu-24.04`: GitHub's hosted runner cannot be pinned by digest. It is already named by version, not `ubuntu-latest`.
- `pyyaml==6.0.2` and `npm ci` from `ui/package-lock.json`: already exact versions.
- Maven plugins and dependencies: they live in the poms and are other cards' work.

### Change readiness

`prime:change-readiness` with `--intent` gave **mitigate first**: "nothing would notice a break: no test imports the touched code". Output: `.prime/tmp/SBJ17-9/readiness/changes/` in the programme folder.

That reason is a false alarm for this change, and I take **proceed with review** instead (SA-3). The tool looks for tests that import code; the touched files are the pipeline itself. A wrong commit makes the step fail to download and the run fail; a wrong digest makes `docker compose up` fail, and if HBase did not start the 2 HBase tests would skip and AC4 fails the maven job. The required checks `maven` and `ui` on the pull request are the check that notices. No inventory or codebase assessment exists for this repository; the tool ran its own inventory.

### Slice

The card description asks only to pin. Risk SBJ17-3's decision also asks to keep a copy of the HBase image in the repository's own package registry. That is a separate thing a person can try, and it needs an act this card's agent cannot take: publishing a package needs a `write:packages` grant the current GitHub login does not have (scopes: gist, read:org, repo, workflow), or a new pipeline job with permission to write packages. Pinning is one slice of about half a day. Proposed split, in this order:

1. This card: pin the steps and the HBase image by digest.
2. A new card after it: copy the HBase image to the repository's package registry, by digest, and point the compose file at the copy.

### Order with other cards

SBJ17-7 (Ready to verify) edits `ci.yml` and adds `test-order.yml`. Decision (mine): Build starts from the newest main; if SBJ17-7 is merged by then, Build pins `test-order.yml` too, else a note on SBJ17-7's file is left for whichever merges second. Every file under `.github/workflows/` on main at build time is in scope.

### Decisions for a person in Plan, each with my default

1. Split as above: pin now, copy the image to the package registry as its own card after. Default: split.
2. Java and Node versions in the pipeline stay on their major line (`'8'`, `'22'`) rather than an exact patch, so they keep getting security fixes. Default: keep the major line.
3. Keep the pins fresh: add `.github/dependabot.yml` so GitHub opens a pull request when a pinned step or the image has a new release. It is a file outside `.github/workflows/`, so outside the "may change" list as written. Default: add it, weekly, for steps and the Docker image.
