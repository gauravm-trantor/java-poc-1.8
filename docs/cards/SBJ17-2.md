### What the card asks

Add a GitHub Actions workflow that builds every module on JDK 8 and runs `mvn clean test` and the UI tests on each pull request and on main. Main can then require it before merging. Today the repository has no `.github` folder and no pipeline.

## Plan, the card lead, 2026-11-27

### Criteria (a person's, word for word)

The question SBJ17-Q1 was answered with all defaults on 2026-11-27. The criteria are copied onto the card's description:

AC1 runs on each pull request to main and push to main. AC2 mvn -B clean test on JDK 8, fails on any failed test. AC3 UI tests in headless Chrome on Node 20.19+, fails on any failure. AC4 the 2 HBase tests run, not skip. AC5 no existing source, pom or test changes.

Also decided by the person: run an HBase service in the pipeline (item 2); the person turns on branch protection after the merge, and this file names the checks (item 3).

### Design

One new file, `.github/workflows/ci.yml`, workflow name `CI`.

- Triggers (AC1): `pull_request` with `branches: [main]` and `push` with `branches: [main]`. `permissions: contents: read`. A `concurrency` group per ref cancels a superseded run.
- Job `maven` (AC2, AC4), on `ubuntu-24.04`:
  1. `actions/checkout@v4`; `actions/setup-java@v4` with `distribution: temurin`, `java-version: 8`, `cache: maven`.
  2. Add `127.0.0.1 host.docker.internal` to the runner's `/etc/hosts`. HBase advertises that name (`docker/local/hbase-server-site.xml`); Docker Desktop adds it on Windows, a Linux runner does not.
  3. Start HBase with the repository's own setup, unchanged: `docker compose -f docker/local/docker-compose.yml up -d hbase` (only the `hbase` service; the Spark services need an image the runner does not have). Not a `services:` container, because the service needs the repository's `start-hbase.sh` and site file mounted, and services start before checkout.
  4. Wait until HBase is ready, at most 5 minutes: ports 2181, 16000 and 16020 answer on localhost and `echo status | docker exec -i sales-hbase hbase shell -n` exits 0. On timeout print `docker logs sales-hbase` and fail.
  5. `mvn -B clean test`. Surefire fails the build on any failed or errored test (AC2). Every module is compiled on JDK 8 by this one command.
  6. Guard step (AC4): read `spark-job/target/surefire-reports/TEST-com.example.salesbatch.spark.SalesAggregatorHBaseTest.xml`; fail unless `tests="2"`, `skipped="0"`, `failures="0"`, `errors="0"`. Without it a missing HBase would silently turn 67 passed into 65 passed and 2 skipped.
  7. `if: always()`: upload `**/target/surefire-reports/` as an artifact; on failure, `docker logs sales-hbase`.
- Job `ui` (AC3), on `ubuntu-24.04`, independent of `maven`:
  1. `actions/checkout@v4`; `actions/setup-node@v4` with `node-version: 20.19.x` or later in the 20 line (`'20'` resolves to the newest 20.x, at least 20.19), `cache: npm`, `cache-dependency-path: ui/package-lock.json`.
  2. In `ui/`: `npm ci`, then `npx ng test --watch=false --browsers=ChromeHeadless`. The runner image has Google Chrome. Karma exits non-zero on any failed spec (AC3).
- AC5 is held by the diff: the change adds `.github/workflows/ci.yml`, files under `scripts/ci/` (the acceptance checks) and `docs/cards/`. No source, pom, test, UI config or `docker/` file changes.
- Check names for branch protection (item 3): `CI / maven` and `CI / ui` as GitHub lists them (the job ids are `maven` and `ui`; no `name:` override, so the names stay stable).

### Acceptance tests (for Test design)

Each criterion gets one check whose name starts with its number, under `scripts/ci/` (scripts are on the may-change list). A sketch, Test design fixes the final form:

- `AC1-triggers.sh`: parses `ci.yml` and asserts `pull_request` and `push` both list `main`.
- `AC2-maven-fails-on-failure`: the pipeline run is the proof that the job passes; the sensitivity check is a throwaway branch (never merged, deleted after) that adds one new failing JUnit test and shows the `maven` check red. No existing test is touched (SA-2).
- `AC3-ui-fails-on-failure`: the same for one new failing Jasmine spec on a throwaway branch, `ui` check red. Plus a static check that the job's Node is 20.19 or newer and the browser is `ChromeHeadless`.
- `AC4-hbase-tests-ran.sh`: the guard step itself, run as a script from the workflow, so it is one numbered test. Sensitivity: run it against a report with `skipped="2"` and see it fail.
- `AC5-no-existing-file-changed.sh`: `git diff --name-only --diff-filter=MDR origin/main...HEAD` is empty outside `docs/cards/`, and every added file is under `.github/`, `scripts/ci/` or `docs/cards/`.

### Roadmap

Commit, push, open the draft pull request, link it. Expected: AC4 fails (no HBase run yet, no report); AC1 and AC5 may already pass because the first `ci.yml` has its triggers. 3. Build: add the hosts line, HBase start and wait; see 67 of 67 and the guard green.
4. Build: add job `ui`; see 25 of 25.
5. Build: sensitivity runs for AC2 and AC3 on throwaway branches, linked in this file, then the branches are deleted.
6. Build: pipeline green on the latest commit with the checks unchanged; mark the pull request ready; this file names the two checks for branch protection.

### Risks seen in the design

- The old third-party image `harisekhon/hbase:1.4` (already raised, SBJ17-3). If the pull fails, step 3 fails; the fallback is the person's choice under SBJ17-3.
- Chrome on `ubuntu-24.04`: AppArmor limits on user namespaces can stop Chrome's sandbox. The runner's own Google Chrome has a profile, so `ChromeHeadless` should start. If it does not, the builder moves the `ui` job to `ubuntu-22.04` (a pipeline change only) rather than editing `ui/karma` or `angular.json`, which are not on the may-change list.
- HBase start time on a 2-CPU runner: the wait is 5 minutes and the two tests have their own 180 s timeouts.

### Decisions I took

- HBase started by `docker compose ... up -d hbase` from the repository's own `docker/local` files rather than a `services:` container, because it needs the mounted start script and site file (SA-3: the agent picks the tool).
- A guard step for AC4, because an `assumeTrue` skip is not a failure and would hide a missing HBase.
- Actions pinned to major tags (`@v4`), the common practice; pinning to commit hashes can come with a later security card.

## Test design, the card lead, 2026-11-27

### The acceptance tests

Commit f39e6b2, before any build. Python 3 scripts under `scripts/ci/`, one per criterion, each named after its number. They print `PASS ACn` or `FAIL: why` and exit 0 or 1. AC1 to AC3 need PyYAML (the pipeline installs `pyyaml==6.0.2`).

| Criterion | Test | What it checks |
|---|---|---|
| AC1 | `AC1-triggers.py` | `ci.yml` runs on `pull_request` and `push`, both including `main` |
| AC2 | `AC2-maven-on-jdk8.py` | a job sets up Temurin JDK 8 and runs `mvn -B clean test`, with no flag, `continue-on-error` or `\|\| true` that hides a failed test |
| AC3 | `AC3-ui-headless-chrome.py` | a job sets up Node 20.19 or newer and runs `ng test --watch=false --browsers=ChromeHeadless`, with nothing that hides a failure |
| AC4 | `AC4-hbase-tests-ran.py [report]` | the Surefire report of `SalesAggregatorHBaseTest` shows 2 tests, 0 skipped, 0 failed, 0 errors |
| AC5 | `AC5-no-existing-file-changed.py [base]` | against `origin/main`, no existing file is changed, removed or renamed (except `docs/cards/`), and new files are only under `.github/workflows/`, `scripts/ci/`, `docs/cards/` |

AC1 to AC3 read the pipeline file; the pipeline's own run shows the jobs do what the file says. The part of AC2 and AC3 a file cannot show, "fails on any failed test", is shown by the sensitivity runs below, which Build must make.

`.github/workflows/ci.yml` in this commit has one job, `acceptance`, that runs the five checks, each step `if: always()`. Build adds the `maven` and `ui` jobs and moves the AC4 step into `maven`, after `mvn -B clean test`. The scripts stay unchanged.

### Changes to the design found here

- Node: Node 20 reached end of life in April 2026. AC3 asks for 20.19 or newer, so Build uses Node 22 (`node-version: '22'`), which Angular 20 supports (`^20.19 || ^22.12 || ^24`). The AC3 check accepts it.
- Actions: the run warns that `actions/checkout@v4` and `actions/setup-python@v5` target the deprecated Node 20 action runtime. Build moves to the current majors (`checkout@v5`, `setup-java@v5`, `setup-node@v5`, `setup-python@v6`, `upload-artifact@v5`) where they exist.
